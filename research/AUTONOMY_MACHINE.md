# 토큰 최적화 자율 목적 달성 기계 — 진단과 설계 (BD-394)

명칭: 기계 전체 = **GA Engine**, 라이브러리 = GA Core(SDK), 입구 = GA CLI · GA API · GA MCP · GA UI — research/NAMING.md.

사용자 목표(2026-10-05): 추상적인 과제(예: "Electron 데스크톱 셸 설계 · 구현")를 받아 사람 개입 없이 완성하고 최종 보고만 하는 기계. 사람 대신 검증하고, 사람 대신 수정 지시를 내려 다시 달성하는 검증자가 들어 있어야 하며, 그 반복이 토큰을 폭발시키지 않아야 한다.

## 1. 실측: 토큰은 어디로 갔나

**허브 방식 장부(RW1, Token MVP 33 작업, Claude Code 세션):**

| 항목 | 토큰 | 비율 |
|---|---|---|
| cache read(매 턴 지난 대화 전체 다시 읽기) | 126,260,219 | **96.4%** |
| cache write | 3,586,194 | 2.7% |
| output(모델이 실제로 쓴 것) | 1,047,496 | **0.8%** |
| input(새 입력) | 44,474 | 0.03% |

- 작업 하나가 평균 380 만 토큰을 다시 읽었다. 쓴 것은 3 만 2 천이다. 총 $57.21.
- **낭비의 정체는 출력이 아니라 "턴 수 × 쌓인 문맥"이다.** 대화형 에이전트는 턴마다 처음부터 다시 읽고, 턴이 늘수록 읽을 양도 는다(대략 제곱으로 증가).

**agy(Antigravity):**
- 턴마다 고정으로 약 10,000 입력 토큰이 든다. 도구 57 개의 정의 때문이다.
- `--continue` 를 써도 캐시되지 않았다(cache_read 383).
- 채팅 모델이 루프를 구동하고 기다리는 데 쓴 비용이 주간 쿼터의 60% 였다(BD-386).

**ga 백엔드별 턴당 고정 비용:**

| 백엔드 | 고정 비용 |
|---|---|
| claude_cli(bare) | 945–1,197 |
| HTTP API | ≈0 |
| agv(agy) | ≈10,000 |

**검증자의 가치(이번 세션):**
- 작업자가 "다 됐다"고 보고한 결과 3 건(GC25, GC18, 앞서 GC31 · GC41)에서 baseline 의 변이 시험이 빈 곳을 찾았다.
- 사람 대신 검증하는 역할은 효과가 확인됐다. 다만 지금은 baseline(모델)이 손으로 하고 있다.

## 2. ga-sdk 가 이미 가진 것과 빠진 절반

**가진 것:**
- 양식: directive / report / work. 양식 검사는 코드가 한다.
- ga mail.
- judge: 시험 실행 · JUnit · 기존 실패와 구분.
- 노드별 worktree, 의존(after), 파일 소유(files), 통과한 것만 fast-forward 통합(GA34).
- L0 기록, 예산 상한, ctxpack(문맥 압축 · 토큰 상한), 백엔드 플러그인, rlo 가드.

**빠진 것:**
1. **계획기:** 추상 과제 → 시험 가능한 작업 그래프. 지금은 ARCH 세션(GC0, $12.36)과 baseline 이 손으로 한다.
2. **자동 검증자:** 변이 · 경계 · 비밀 검사를 하고, 수정 지시를 자동으로 낸다. 지금은 baseline 이 손으로 한다.
3. **값싼 실행기:** 지금은 대화형 에이전트(Claude Code · agy)에게 통째로 맡긴다. 그래서 위의 96% 낭비가 생긴다.
4. **진전 감지 루프:** 같은 실패의 반복을 알아채고 모델 승격 · 재계획 · 막힘 보고 중 하나로 넘긴다. 지금 rlo 재시도는 처음부터 다시 한다.
5. **비용 라우터:** 단계마다 싼 모델 / 비싼 모델을 고른다. GA31 의 catalog 는 있지만 실행 루프에 연결돼 있지 않다.

## 3. 설계 원칙

1. **모델은 결정만, 나머지는 코드.** 읽기 · 찾기 · 실행 · 시험 · 기다리기 · 양식 · 판정 · 병합은 코드가 한다. 모델 토큰은 "무엇을 바꿀지" 에만 쓴다.
2. **도구를 프롬프트에 싣지 않는다.** 57 개든 500 개든 도구는 코드 쪽 능력이다.
   - 모델은 고정된 작은 **행동 형식** 하나로만 답한다(아래 4.2).
   - 명령은 이름만 고른다(`RUN test`). 이름 목록은 그 작업에 관련된 몇 줄만 실린다.
   - 그래서 도구 수가 늘어도 프롬프트는 늘지 않는다.
3. **대화 기록 대신 고정 크기 상태 카드.** 매 턴 새로 조립한다. 들어가는 것은 과제 카드, 현재 빨간 시험 요약, 관련 코드 조각, 직전 변경 요약이다. 턴이 늘어도 입력은 일정하다(96% 문제의 직접 처방). 변하지 않는 앞부분(형식 설명 · 과제 카드)은 API 프롬프트 캐시를 탄다.
4. **문맥은 모델이 찾지 않고 코드가 미리 가져온다.** 심볼 지도 · import 그래프 · 시험 실패 스택에서 관련 파일 · 함수만 뽑는다. 모델은 `NEED symbol X` 로 더 요청할 수 있고, 다음 턴에 코드가 채운다.
5. **판정은 실행 가능한 것이 먼저.** 수용 시험을 구현보다 먼저 만들고, 자동 변이로 그 시험의 힘을 잰다. LLM 판정은 실행할 수 없는 기준(설계 품질 등)에만, 채점표와 작은 문맥으로 쓴다.
6. **재시도는 정보를 가지고 한다.** 다음 턴은 "무엇이 아직 빨간가" 의 차이만 받는다. 같은 실패 집합이 2 번 나오면 진전 없음으로 보고 다음 중 하나로 넘긴다: 강한 모델로 승격 → 재계획 → `blocked` 보고. 무한 재시도는 없다.
7. **단계별 모델 · 백엔드 라우팅.**
   - 계획 · 재계획 · 막힘 진단 = 강한 모델 1–2 턴.
   - 편집 반복 = 싸고 빠른 모델, 고정 비용이 낮은 백엔드(claude_cli bare, HTTP + 캐시, 로컬 OpenAI 호환 서버).
   - agy 는 고정 비용이 커서 작은 편집 턴에는 맞지 않는다. 큰 계획 턴처럼 고정 비용이 묻히는 곳에만 쓴다.
8. **사람은 끝에만.** 최종 report/2 와 needs(자격 증명 · 예산 · 새 저장소)만 사람에게 간다.

## 4. 구조

사용자 지시(2026-10-05): **SDK 는 Claude · Antigravity · Codex 등 모델과 관계없이, 모델 위 최상위 계층에서 자연어로 쓴 사용자 요구를 semantic 하게 가공하고 시작해야 한다.**
→ 맨 앞 단계는 접수(intake)다. 어떤 모델이든 같은 지시 · 같은 출력 양식(task/1)을 쓰고, 백엔드는 라우터가 고른다. 벤더 고유 도구는 쓰지 않는다.

```
자연어 요구 ──▶ [접수] 코드가 저장소 요약(≤2k) + 모델 1턴(어느 벤더든) ─▶ task/1 명세(목표 · 산출물 · 제약 · 확인 가능한 수용 기준 · 비목표 · 가정+기본값 · 막는 질문만)
                  │ 코드가 검사(모호한 기준 표시, 1회 고침, 아니면 blocked)
                  ▼
추상 과제 ──▶ [계획기] 강한 모델 1–2턴 ─▶ 작업 그래프(work/1: 목표 · files · after · 수용 시험 argv)
                  │ 코드가 검사(양식 · 순환 · 소유 겹침)
                  ▼
          [풀 · 스케줄러] (GA34) ─ 작업마다 worktree
                  ▼
          [실행기] 루프: 상태 카드 → 모델(행동 형식) → 코드가 적용 · RUN → 결과 요약 → 상태 카드 …
                  ▼
          [검증자] ga judge(시험) + 자동 변이 + 경계 · 비밀 · 소유 검사 (+ 필요할 때만 LLM 채점)
             ├─ 통과 → fast-forward 통합
             └─ 실패 → 수정 지시(빨간 시험 · 생존 변이) → 실행기 (진전 없으면 승격 · 재계획 · blocked)
                  ▼
          최종 보고(report/2) + 토큰 장부
```

### 4.0 접수 · 최상위 계층(GA37) — 모델 무관
- 입구는 `ga do "<자연어 요구>"` 하나다.
- 코드가 먼저 저장소를 요약한다: 언어, 빌드 · 시험 명령, 트리, README 머리, 기존 ga 설정. ctxpack 상한은 2k 다.
- 모델 1 턴(라우터가 고른 아무 백엔드)이 task/1 을 JSON 으로 낸다.
- 코드가 그 출력을 검사한다:
  - 수용 기준마다 명령 · 파일 · 관찰 가능한 결과 중 하나가 있어야 한다.
  - 모호한 낱말은 표시한다.
  - 문제가 있으면 1 회 고치게 하고, 그래도 안 되면 blocked 다.
- 자율 규칙: 사람에게 묻는 것은 needs(자격 증명 · 예산 · 새 저장소 · 되돌릴 수 없는 일)뿐이다. 나머지는 가정과 기본값으로 정해 명세와 최종 보고에 적는다.
- 같은 프롬프트로 5 개 내장 백엔드(claude_cli · agv · codex_cli · openai_http · anthropic_http) 모두에서 동작해야 한다.

### 4.1 계획기(GA40)
- 입력: 과제 문장과 저장소 요약(코드가 만든 심볼 지도).
- 출력: work/1 목록. 항목마다 files, after, done_when(argv) 와 수용 시험 초안을 둔다.
- 검사: 양식 · 순환 · 소유 겹침 · 시험 argv 실행 가능 여부.
- Token MVP 의 roadmap 표가 사람(ARCH)이 만든 정답 예시다. 학습 · 회귀 자료로 쓴다.

### 4.2 실행기와 행동 형식(GA38) — "TS 처럼 약속된 형식"
모델의 답은 아래 블록들만 담는다. 형식 설명은 약 300 토큰이고 매 턴 같아서 캐시된다.

```
EDIT path/to/file.py
<<<<<<< SEARCH
(기존 줄, 정확히)
=======
(새 줄)
>>>>>>> REPLACE
NEW path/to/new_file.py
(내용)
RUN test            # 이름만: 저장소 설정의 허용 명령(argv 고정)
NEED symbol app.domains.run.router.monitor_snapshot
DONE | BLOCKED <이유>
```

- 코드가 하는 일:
  - 형식을 검사한다.
  - 소유 파일 안에서만 적용한다. SEARCH 가 정확히 맞지 않으면 그 블록만 거절하고, 어긋난 줄을 다음 카드에 넣는다.
  - RUN 을 실행하고, 결과를 요약해 다음 카드에 넣는다(실패 시험 이름 · 핵심 스택 몇 줄).
- 도구 수 제한이 없다. "도구" 는 허용 명령 이름(`test`, `lint`, `typecheck`, `build`, `e2e` …)과 코드 쪽 검색기(symbol · grep · 의존 그래프)다. 프롬프트에는 작업에 관련된 이름 몇 줄만 들어간다.
- 백엔드는 무엇이든 된다. 도구 호출 기능이 없는 모델(로컬 gpt-oss 등)도 텍스트 형식만 지키면 된다.

### 4.3 자동 검증자(GA39) — baseline 이 손으로 하던 일의 코드화
- 시험: ga judge.
- 변이: 바뀐 줄에 AST 연산자를 적용한다. 조건 제거, 비교 반전, 호출 삭제, 상수 변경 등이다. 시험이 하나도 실패하지 않으면 그 변이는 "생존" 이다.
- 생존 변이 → 수정 지시: "이 줄을 이렇게 바꿔도 시험이 통과한다. 이를 잡는 시험을 추가하라".
- 그 밖의 검사:
  - 경계: 도메인이 api.py 로만 서로를 부르는지(import 검사).
  - 비밀 패턴.
  - 소유 밖 파일 변경.
- LLM 채점: 실행 불가능한 기준에만, 작은 문맥으로. 강한 모델 1 턴.
- 출력: verdict 양식, 그리고 다음 수정 지시(directive rev n+1).

### 4.4 루프 정책 · 라우터(GA41)
- 상한: 작업마다 턴 · 토큰 상한, 전체 그래프 예산.
- 진전 감지: 빨간 시험 집합과 생존 변이 수의 변화로 판단한다.
- 단계 전환: 싼 모델 → 강한 모델 → 재계획 → blocked.
- 장부: 모든 턴(백엔드 · 모델 · 입력 · 캐시 · 출력 · 초)을 기록한다.

## 5. 성공 기준(측정 가능)

RW1(b): Token MVP 에서 이미 사람 · 허브 방식으로 끝낸 작업 몇 개를 같은 수용 시험으로 다시 수행해 비교한다. 비교 대상은 장부와 같은 항목이다.

| 지표 | 목표 |
|---|---|
| 작업당 총 토큰 | 허브 방식의 1/5 이하 |
| judge 통과 | 같아야 함 |
| baseline 변이 생존 | 0 |
| 사람 개입 | 0 |
| 출력 대비 읽기 비율 | 96% → 크게 낮춤(상태 카드 효과) |

후보 작업: GC25(estimation 라우터 · PG 저장소), GC18(키 보관), IF1(Electron 셸). 수용 시험은 이미 저장소에 있다.

## 6. 순서

1. **GA37 접수(최상위 계층, 모델 무관) + `ga do` 입구 · task/1 양식.** GA38 과 나란히 진행한다(파일이 겹치지 않음).
2. **GA38 실행기 + 행동 형식 + 상태 카드.** 가장 큰 낭비(96%)를 직접 친다.
3. **GA39 자동 검증자 + 수정 지시 생성.** 사람 대신 검증 · 재지시.
4. **GA40 계획기.** task/1 → 작업 그래프.
5. **GA41 루프 정책 · 라우터 + RW1(b) 비교.** `ga do` 가 처음부터 끝까지 이어진다.
6. GA36(ga ask · ui)은 이 기계의 앞문(질문 · 진행 · 토큰 표시)이 된다. 그 안의 Solve 는 `ga do` 로 바꿔 끼운다.

BD-393 의 GA37(agy 도구 켜기)과 GA38(ga mcp 플러그인) 계획은 이 설계로 대체한다. agy 자체 도구로 편집하면 턴당 10k 고정 비용에 대화형 재읽기까지 더해지기 때문이다(사용자 지적과 같은 결론).

## 7. 시험대: 사용자의 실제 프롬프트 (BD-395)

사용자(2026-10-05): "내가 너에게 던지는 이러한 요구들을 자율적으로, 토큰 사용을 최소화하며 달성해야 한다. 지금 내가 적었던 프롬프트를 SDK 에게 시킬 것이다."

**프롬프트의 모양(이 대화에서 관찰, 원문은 사용자가 직접 넣는다):**

| 종류 | 예 | 기계에 필요한 것 |
|---|---|---|
| 질문 · 진단 | "왜 이런 현상이 발생하는가?", "어느 레포 브랜치에 있지?" | 답하기(answer): 코드 · 기록 · 로그를 코드가 찾아 근거와 함께 짧게 답한다. 바꾸는 일은 없다 |
| 조사 · 비교 | "LangChain, LlamaIndex, DSPy 랑 비교해줘", "쿼터 소모량을 비교해보아라" | 조사(investigate): 측정 · 실험이 필요하면 계획 → 실행 → 표 |
| 변경 · 구축 | "Electron 셸 설계 · 구현", "터미널을 감싸는 프론트엔드가 필요하다" | 변경(change): 접수 → 계획 → 실행 → 검증 → 통합 |
| 결정 · 방향 | "A 로 간다", "추천대로 해", "프롬프트 최적화는 하지 말자" | 결정(decide): 프로젝트 상태(결정 기록)를 바꾸고, 진행 중인 일에 반영한다 |
| 짧은 조각 | "1번", "시작해", "정리해줘", "어디까지 되었어?" | 프로젝트 상태 없이는 뜻이 없다 → 직전 제안 · 진행 상태를 기억하는 상태 저장소가 필수 |
| 붙여넣기 | 다른 도구의 출력, 오류 로그 | 진단 입력. 비밀처럼 보이는 것은 가린다 |

**설계에 더하는 것:**
- task/1 에 `kind: answer | investigate | change | decide` 를 둔다. 접수가 고르고, 종류마다 다음 단계가 다르다.
  - answer 는 계획기 · 실행기를 거치지 않고 끝난다. 가장 싸다.
- **프로젝트 상태 저장소:**
  - 결정 기록, 직전 제안(번호 붙은 선택지), 진행 중인 작업, 열린 요청을 담는다.
  - baseline 의 DECISION_LOG · OPEN_REQUESTS 와 같은 역할을 코드가 한다.
  - 짧은 조각은 이 상태로 풀고, 풀 수 없으면 needs 가 아니라 "가장 최근 제안" 으로 가정하고 적는다.
- **재생 모드:** `ga do --replay prompts.txt`. 사용자가 준 프롬프트 목록을 순서대로, 같은 상태 저장소로 처리한다. 프롬프트마다 다음을 장부에 적는다:
  - 토큰 · 비용
  - 사람에게 물은 수
  - 결과(답 · 변경 sha · blocked 이유)

**비교 기준:** 같은 요구들을 이 허브(baseline 세션 + 작업 세션)가 처리한 비용. RW1 장부와 baseline 세션 사용량.

**성공:**
- 같은 결과(시험 통과 · 답의 근거)를 낸다.
- 사람 개입은 needs 만 있다.
- 토큰은 허브 방식의 1/5 이하다.
