## 1. 무엇·왜

**무엇.** `9398322`이 바꾼 파일은 `.github/workflows/engine.yml` 하나(+40 −1)다. 두 가지다.

1. web 작업의 `npm install`에서 `http-server`를 `http-server@14.1.1`로 고정(92줄).
2. 세 번째 작업 `deploy`를 추가(116–153줄): web 작업이 시험을 통과시킨 `site` 묶음을 내려받아 그대로 GitHub Pages에 올리고,
   배포된 실제 주소로 같은 smoke 시험을 한 번 더 돌린다.

Pages를 "GitHub Actions 방식"으로 켜는 일은 VM이 API로 했다(코드가 아니라 저장소 설정이라 이 커밋에는 없다. DEVLOG VM-19 항목).

```text
push (main)            : engine ──► web ──(site 산출물)──► deploy
                                                         ├ ① download-artifact  site
                                                         ├ ② upload-pages-artifact (Pages용 묶음)
                                                         ├ ③ deploy-pages  → outputs.page_url
                                                         └ ④ smoke.mjs  (SITE_URL = page_url)
push (vm/*), pull_request: engine ──► web               deploy = skipped
```

**왜 main에서만 배포하나.**
- SPEC 6.1: "Pages 배포 환경은 기본적으로 기본 브랜치(`main`)에서만 배포를 허용한다. 작업 브랜치는 빌드·시험만 하고, 배포는 `main` 병합 시 실행한다."
- DEVLOG의 결정(10-08 23:5x): "배포: main 병합 시에만". 공개 주소에 올라가는 것은 언제나 "CI 시험 통과 + top이 검토하고 병합한 커밋"이어야 한다.
  작업 브랜치에서 배포하면 아직 불합격일 수 있는 rev 1(VM-18의 `716d3ac`처럼 CI가 녹색인데 불합격인 것)이 공개된다.
- 119줄 `if:`가 없으면 작업 브랜치 push에서도 deploy 작업이 시작되고, Pages 환경의 브랜치 규칙에 막혀 **실패**로 끝날 것이다(SPEC 6.1의 설명대로라면).
  `if:`로 걸러 두면 "실패"가 아니라 "건너뜀(skipped)"이 되어, 작업 브랜치의 CI 결과가 녹색으로 남는다. 실제 기록: `9398322`의 push run과
  pull_request run 둘 다 `deploy skipped`(4장).

**왜 다시 빌드하지 않고 `site` 산출물을 내려받나.** web 작업은 `site/`를 묶은 뒤 그 묶음을 http-server로 열어 smoke 시험을 통과시키고(95–100줄),
같은 폴더를 `site` 산출물로 올린다(108–113줄). deploy가 그 산출물을 받아 올리면 **시험을 통과한 바이트 그대로**가 공개된다.
deploy에서 다시 빌드하면 Emscripten 설치·WASM 빌드를 한 번 더 해야 하고, 시험한 것과 배포한 것이 같다는 보장도 사라진다.
`needs: web`(118줄)이 "web이 성공했을 때만"과 "산출물이 이미 올라가 있음"을 둘 다 보장한다.

**왜 `permissions: pages: write` + `id-token: write`인가.**
- `pages: write`: `deploy-pages`가 이 저장소에 Pages 배포를 만들 권한.
- `id-token: write`: 작업이 GitHub의 OIDC 토큰을 발급받을 권한. `deploy-pages`는 이 토큰으로 "이 배포 요청은 이 저장소의 이 워크플로 실행에서 왔다"를
  Pages 쪽에 증명한다. 저장소 비밀값(PAT 등)을 따로 두지 않아도 된다.
- 작업 단위 `permissions:`를 쓰면 **적은 것만** 주어지고 나머지 권한은 없음이 된다. 그래서 engine·web 작업은 이 두 권한을 갖지 않는다 —
  배포 권한은 deploy 작업에만 있다. (참고: `contents` 권한을 적지 않았지만 이 저장소에서 deploy 작업의 checkout 단계는 성공했다. 4장.)

**왜 `environment: github-pages`인가.** Pages를 Actions 방식으로 켜면 저장소에 `github-pages`라는 배포 환경이 생기고, SPEC 6.1이 말한 "기본 브랜치에서만"
규칙이 이 환경에 걸린다. 작업이 이 환경을 선언해야 `deploy-pages`가 그 환경으로 배포하고, 배포 기록이 저장소의 Deployments 목록에 남는다
(4장: `c1cbeed`, `a78196a` 두 건). `url:`(122줄)은 그 기록과 Actions 실행 화면에 배포 주소 링크를 단다.

**http-server 고정.** VM-18의 CI 로그상 설치된 버전이 14.1.1이었다(code/03 3.11절). 그 버전을 그대로 적어, 나중에 새 버전이 나와도 smoke 시험의 조건이 바뀌지 않게 한다.
Playwright는 이미 `1.47.2`로 고정되어 있었다(SPEC 6.2 고정 버전).

읽을 때 주의할 점(코드가 하는 일 그대로):
- `${{ … }}`는 쉘이 아니라 Actions가 실행 전에 글자로 바꿔 넣는다. 값이 `deploy-pages`의 출력(GitHub이 만든 주소)이라 여기서는 문제없지만,
  사용자가 쓴 값(PR 제목 등)을 이렇게 `run:` 안에 넣으면 명령 주입이 된다. 습관적으로는 `env:`로 넘기는 편이 안전하다(연습 문제 5).
- deploy의 smoke는 화면에 커밋 해시가 **보이는지 검사하지 않는다**. SPEC 6.2 deploy 줄 "화면에 커밋 해시 표시"는 web 작업의 `sed`(87줄)가
  만들고, 실제 주소에서의 확인은 VM-21이 HTTP로 받아 따로 했다(4장).
- smoke.mjs는 `smoke-screenshot.png`를 찍지만 deploy 작업에는 업로드 단계가 없어 그 스크린샷은 버려진다.
- 실패해도 되돌리는 단계가 없다. 배포(140–142줄) **뒤에** 시험(150–153줄)하므로, 실제 주소의 smoke가 실패하면 깨진 페이지가 이미 공개된 상태로 작업만 빨간색이 된다.
  배포 전 같은 바이트를 localhost에서 시험했기 때문에(web 작업) 이 순서를 받아들인 것이다.
- 같은 main에 병합이 빠르게 두 번 오면 deploy 두 개가 겹칠 수 있다. `concurrency:`가 없다(연습 문제 6).

## 5. 연습문제

1. 119줄에서 `github.event_name == 'push' &&`를 지우면, main을 대상으로 한 PR 실행에서 deploy가 도는가? `github.ref`의 값으로 설명하라.
2. 118줄 `needs: web`을 지우면 어떤 일이 생기나? 두 가지를 적어라.
3. 125줄 `id-token: write`를 지우고 main에 병합하면 어느 단계에서 실패할 것으로 예상하나? (실행하지 않고 예측만.)
4. 배포된 주소의 smoke에 "화면의 커밋 해시 = `GITHUB_SHA`" 검사를 더하라. smoke.mjs와 워크플로 중 어디에 무엇을 고치나?
5. 150–153줄을 `${{ }}`를 `run:` 안에 직접 쓰지 않는 모양으로 바꿔라.
6. main에 병합이 1분 간격으로 두 번 오면? 겹치는 배포를 막는 설정을 적어라.
7. deploy 작업의 스크린샷도 남기되, 실제 주소 smoke가 **실패할 때도** 남게 하라.

### 정답 (접어 둠)

<details>
<summary>1–3</summary>

1. 돈다고 보기 어렵다. pull_request 실행의 `github.ref`는 `refs/pull/<번호>/merge`라서 `== 'refs/heads/main'`이 거짓이다. 즉 지금 워크플로에서는
   ref 조건만으로도 PR은 걸러진다. `event_name` 조건은 뜻을 분명히 하고, 나중에 `workflow_dispatch` 같은 다른 이벤트를 더했을 때(그 경우 ref가
   `refs/heads/main`일 수 있다) "push만"이라는 의도를 지킨다.
2. (가) web이 실패해도 deploy가 시작된다 — 시험에 떨어진 페이지가 공개될 수 있다. (나) deploy가 web과 동시에 시작되어 `site` 산출물이 아직
   올라가기 전에 `Download Static Site`가 실패한다. `needs`는 순서와 성공 조건을 함께 준다.
3. `Deploy to GitHub Pages`(140–142줄). OIDC 토큰을 발급받지 못해 배포 요청을 증명할 수 없다. `Upload Pages Artifact`까지는 성공할 것으로 예상한다.
   (이 세션에서 실행하지 않은 예측이다.)

<details>
<summary>4–5</summary>

4. smoke.mjs에 환경 변수 `EXPECTED_SHA`가 있으면 `await page.textContent('#commitHash')`와 비교해 다르면 `process.exit(1)` 하는 몇 줄을 더한다.
   워크플로의 deploy 단계에는 `EXPECTED_SHA: ${{ github.sha }}`를 `env:`로 넘긴다. web 작업(localhost)에도 같은 값을 넘기면 `sed` 치환까지 시험된다.
   `EXPECTED_SHA`가 없을 때는 검사를 건너뛰어 로컬 실행을 깨지 않게 한다.
5. 단계에 `env:` 아래 `SITE_URL: ${{ steps.deployment.outputs.page_url }}`를 두고, `run:`은 `node trip_optimizer/web/tests/smoke.mjs` 한 줄만 남긴다
   (`export` 줄 삭제). 값이 쉘 스크립트의 글자가 아니라 환경 변수로 들어가므로, 값 안에 따옴표·`$(...)`가 있어도 명령으로 해석되지 않는다.

<summary>6–7</summary>

6. 지금은 두 deploy가 겹칠 수 있다. 워크플로나 deploy 작업에 `concurrency:` 아래 `group: pages`, `cancel-in-progress: false`를 두면 같은 그룹의 배포가 한 번에 하나씩 돈다. `false`로 두는 이유: 진행 중인 배포를 중간에 끊지 않고, 대기 중인 것은 최신 하나만 남는다.

   `web` 작업의 `smoke-screenshot`과 이름이 겹치지 않게 다른 이름을 쓴다.
