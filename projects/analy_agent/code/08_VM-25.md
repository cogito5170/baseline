**왜 "시간 → 분, 반올림, 정수"인가.** SPEC 3.1의 목적 함수 줄(`git show d1fdae0:trip_optimizer/SPEC.md`의 49–51줄):

```text
- **목적 함수:** 구간 가격 합 + 숙박비 합 + (분당 시간 가치) × 이동 시간 합.
  - 모든 금액과 시간은 **정수(원, 분)**로 계산한다. 그래서 결과가 플랫폼과 무관하게 정확히 같다.
  - UI의 "1시간의 가치(원)"는 분 단위로 반올림해 엔진에 넘기고, 실제로 쓴 값을 화면에 표시한다.
```

엔진(code/00)은 `int64` 정수로만 계산한다. 사람은 "내 1시간은 만 원"처럼 시간 단위로 생각하지만, 엔진의 이동 시간은 분이다. 그래서 경계(UI)에서 한 번
나누고, 소수가 생기면 **정수로 반올림해서** 넘긴다. 그러면 같은 입력이면 어떤 플랫폼에서도 목적값이 정확히 같다(V4의 전제). 대신 화면에는 "실제로 쓴 값"을
보여 줘야 한다 — 10,000원/시간을 넣은 사람은 실제로 167원/분(= 10,020원/시간)으로 계산된 결과를 받기 때문이다(2.1절).

**반올림을 직접 보자.** 위 식과 같은 `Math.round((h || 0) / 60)`을 node로(`scratchpad/trip25/round.mjs`, 4장):

```text
hour      0  h/60 =         0  Math.round -> 0
hour  10000  h/60 =  166.6667  Math.round -> 167
hour  12000  h/60 =       200  Math.round -> 200
hour     90  h/60 =       1.5  Math.round -> 2
hour     30  h/60 =       0.5  Math.round -> 1
hour     29  h/60 =    0.4833  Math.round -> 0
hour     59  h/60 =    0.9833  Math.round -> 1
hour    -90  h/60 =      -1.5  Math.round -> -1
hour    -30  h/60 =      -0.5  Math.round -> 0
parseInt("") || 0 = 0
parseInt("12000.9") || 0 = 12000
parseInt("1e4") || 0 = 1
parseInt("abc") || 0 = 0
legacy m in 0..100000: toMin(m*60) !== m for 0 values
hours giving 167/min: 9990..10049 (60 values)
```

읽는 법:
- `10000 / 60 = 166.67` → **167**. 지시문의 예이자 V6 시험(`model.test.mjs` 133–143줄)의 값이다. 167원/분 × 60 = 10,020원/시간이므로, 사용자가 넣은 값과
  엔진이 쓴 값이 20원/시간 다르다. 그래서 칸 옆 `(167원/분)` 표시가 필요하다.
- `Math.round`는 .5에서 **+∞ 쪽**으로 올린다: 1.5 → 2, 0.5 → 1, 그러나 −1.5 → **−1**, −0.5 → **0**(실제로는 `-0`이 나오지만 출력에서 `0`). 음수 시간값은 칸의
  `min="0"` 때문에 스핀 버튼으로는 안 나오지만 키보드로는 칠 수 있고, 어느 코드도 막지 않는다(연습문제 2).
- 30원/시간 미만은 0원/분 — 사실상 "최저가 모드"다. 거꾸로 9,990~10,049원/시간 60가지가 모두 167원/분이 된다. 분 단위 정수로 줄이는 대가다.
- `parseInt('12000.9')`은 12000, `parseInt('1e4')`는 **1**이다. `type="number"` 칸은 `1e4`를 유효한 값으로 받으므로 화면은 10000처럼 보이는데 계산은 1원/시간이 된다
  (`Number()`를 쓰면 10000. 연습문제 3).
- 옛 링크 변환(×60)은 손실이 없다: 0..100,000 모든 분당값 `m`에 대해 `Math.round(m × 60 / 60) = m`. 그래서 2.4절의 변환은 3주차 링크의 결과를 그대로 재현한다.

### 2.2 불합격 (a): 거꾸로 된 수정 — 워커 초기화 오류

지시 (2)의 첫 항목은 "요청이 없어도(pending request가 없어도) 워커 초기화 오류를 보여라"였다. 3주차(`023ee43`)의 `worker.onerror`는 이미 **절반은** 하고 있었다:

- 95–103줄 `onerror`: 요청이 있으면 그 Promise를 거부하고, **없으면(`else`) 상태 줄에 `Worker failed to load: …`를 쓴다** — 지시가 원한 바로 그 동작.
- 89–90줄 `onmessage`의 `'error'`: 요청이 없으면 **아무것도 하지 않는다** — 이쪽이 진짜 빈틈이었다. 워커 안의 `init` 처리(`worker.mjs` 8–17줄)는 `Module()`이
  실패하면 `{ type: 'error' }`를 보내는데, 페이지 적재 직후라 요청이 없으므로 이 메시지는 버려진다.

rev 1은 빈틈(89–90줄)은 그대로 두고, 이미 맞던 `else` 가지(99–102줄)를 **지웠다**(2.1절 diff의 `-            else {` 네 줄). 그 결과 워커 모듈이 적재에 실패하면

1. 읽는 쪽은 관대하게: 새 코드는 **모든 옛 형식**을 읽어야 한다. 옛 형식을 새 키로 바꾸는 일은 한 곳(`decodeState`)에서 끝낸다 — 화면 코드는 새 키만 안다.
2. 쓰는 쪽은 새 형식만: `encodeState`는 `costPerHour`만 쓴다(`getInputState` 135줄).
3. 형식에 **버전**을 두면 "키가 있나 없나"로 추측하지 않아도 된다(예: `{ v: 2, … }`. 없으면 v1). 지금은 키 이름이 버전 노릇을 한다(연습문제 6).
4. 옛 링크 시험은 **옛 코드가 실제로 만든 모양**으로 한다. V6의 새 시험(`model.test.mjs` 119–131줄)이 그렇다 — 2.5절에서 rev 1 코드에 돌려 실패를 확인.

### 2.6 F8 격차 보고 (`trip_optimizer/docs/F8_gap_report.md`)

```markdown
# F8 Day Plan Gap Report

## Requirements (SPEC 3.3)
SPEC 3.3 requires that day plans be generated for the trip, providing detailed itineraries within each destination, respecting time constraints, and balancing cost and time to propose a heuristic or exact sequence of activities.

## What Exists
Currently, there is no day plan generation logic. The optimizer only produces city-level legs and stays but does not schedule intraday visits or calculate the exact optimal route within a city.

## Proposed Measurement (Heuristic vs Exact)
We propose measuring the gap by computing both:
1. An exact optimal solution (e.g. using a brute-force approach or ILP solver) for a set of small test cases (up to 10 intra-city points).
2. The heuristic solution using the proposed fast approximation algorithm.

The gap will be measured as the average relative error in objective function value (Time Value + Cost):
`Gap = (Heuristic_Objective - Exact_Objective) / Exact_Objective`

In terms of performance, we will also report the ratio of execution times.
```

비교할 SPEC 3.3 원문(`git show d1fdae0:trip_optimizer/SPEC.md`의 60–63줄)과 F8 줄:

- 장소가 적으면 정확해(완전 탐색)를, 많으면 휴리스틱(삽입 + 2-opt)을 쓴다.

| F8 | 하루 일정: 숙소 기준 관광지·식당 방문 순서, 영업시간 창 고려 | Should |

지시가 요구한 세 가지(SPEC이 요구하는 것, 지금 있는 것 = 없음, 휴리스틱 대 정확해 격차 측정안)는 다 있다. 읽을 때 주의할 점:
- **문제 정의가 SPEC과 다르다.** SPEC은 "시간창이 있는 오리엔티어링 문제 — 다 갈 수 없을 때 무엇을 빼고 어떤 순서로"다. 보고서는 "비용과 시간의 균형"이라고
  적고, 격차의 목적값을 "Time Value + Cost"로 둔다. 오리엔티어링의 목적은 보통 **방문한 장소의 가치 합 최대화**(시간창·예산 제약)라서, 이 식으로는 "무엇을 뺐나"가
  격차에 나타나지 않는다.
- SPEC이 정한 방법(정확해 = 완전 탐색, 휴리스틱 = 삽입 + 2-opt)을 보고서는 "brute-force or ILP", "proposed fast approximation algorithm"으로 흐렸다.
- `Gap = (H − E) / E`는 E = 0이면 정의되지 않는다. 최대화 문제라면 부호도 `(E − H) / E`가 된다.
- 측정 설계에 필요한 것 — 몇 개의 무작위 사례, 장소 수(예: 6, 8, 10), 시간창 생성 규칙, 시드 고정, 보고할 값(평균·최대 격차, 최적과 같은 비율) — 이 없다.
  이것들이 있어야 "시험으로 측정해 보고한다"(SPEC 3.3 셋째 줄)가 재현 가능한 숫자가 된다(연습문제 8).
이번 지시에서 F8은 Should이고 "보고만"이었으므로 수락에는 영향이 없었다.

#   "break": replace `throw e;` inside throwError with `return;` (parser stops throwing).

T=$1; C=$2; MODE=${3:-}

git -C "$REPO" show "$T:trip_optimizer/web/tests/model.test.mjs" > "$W/tests/model.test.mjs"
if [ "$MODE" = break ]; then
  sed -i 's/^        throw e;$/        return;/' "$W/model.mjs"
fi
cd "$W"
node --test --test-reporter=tap tests/model.test.mjs 2>&1 | awk '
  /^(not )?ok |^# (tests|pass|fail) / { print; next }
  /^  error:/ { inerr = 1; if ($0 !~ /\|-$/) print; next }
