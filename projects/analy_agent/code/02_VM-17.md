## 1. 무엇·왜

**무엇.** 같은 C++ 엔진을 Emscripten으로 컴파일해 `engine.mjs` + `engine.wasm`을 만들고(SPEC 4장 그림의 Web Worker가 부를 파일),
네이티브 빌드와 WASM 빌드가 **같은 입력에서 같은 출력 배열**을 내는지 CI에서 증명한다. 이것이 SPEC 5장의 V4다.

> V4 | 네이티브 = WASM | 네이티브 빌드가 무작위 문제와 결과를 기준 파일로 내보내고, Node에서 WASM으로 같은 문제를 풀어 출력 배열을 비교 | 불일치 0

**왜 V4가 따로 필요한가.** V1~V3(오라클 비교, 실재성, 심은 결함)은 네이티브 시험 실행 파일 안에서만 돈다. 그런데 사용자가 실제로 쓰는 것은
브라우저의 WASM이다. 두 빌드는 소스만 같고 나머지는 다르다.

| | 네이티브 (engine 작업) | WASM (web 작업) |
|---|---|---|
| 컴파일러 | GCC 13.3.0 (CI 로그 `The CXX compiler identification is GNU 13.3.0`) | Emscripten 3.1.64 (clang 기반) |
| 표준 라이브러리 | libstdc++ | libc++ |
| 대상 | x86_64, `size_t` 64비트 | wasm32, `size_t` 32비트 |
| 경계 | C 함수 직접 호출 | JS → WASM 힙에 배열 복사 → 포인터 전달 |

그래서 "네이티브 시험이 녹색"이 "브라우저 결과가 맞다"를 보장하지 않는다. V4는 이 차이 전부(컴파일러, 표준 라이브러리, 32비트, JS 경계 코드)를
한 번에 덮는 끝에서 끝 비교다. 정답 기준은 V1~V3로 검증된 네이티브 쪽이다.

**왜 `static_cast`가 필요했나.** `sidx(...)`는 `int`를 돌려주고(198줄 `int sidx(int mask, int city, int day) const`),
`states_`는 `std::vector`라서 `operator[]`의 인자 형은 `size_type`(= `size_t`, 부호 없음)이다. 그래서 87줄에서 `int → size_t`
**부호 변환**이 암묵적으로 일어난다. 같은 파일의 다른 자리(98, 114, 136, 157줄)는 이미 `static_cast<size_t>(...)`로 감싸져 있었고
87줄 하나만 빠져 있었다.

이 경고를 누가 내는지는 직접 확인했다(아래는 `e081fb3`을 `/tmp/claude-0/vm17/src_e081`에 풀어 저장소 루트처럼 놓고 실행한 결과).
엔진 라이브러리의 경고 옵션 `-Wall -Wextra -Wconversion -Wshadow`를 그대로 썼다.

```text
$ g++ -std=c++17 -Itrip_optimizer/engine/include -Wall -Wextra -Wconversion -Wshadow -fsyntax-only trip_optimizer/engine/src/optimizer.cpp
(출력 없음, rc=0)

$ clang++ -std=c++17 -Itrip_optimizer/engine/include -Wall -Wextra -Wconversion -Wshadow -fsyntax-only trip_optimizer/engine/src/optimizer.cpp
trip_optimizer/engine/src/optimizer.cpp:87:42: warning: implicit conversion changes signedness: 'int' to 'size_type' (aka 'unsigned long') [-Wsign-conversion]
   87 |                     push_bounded(states_[sidx(1 << (j - 1), j, d)], Entry{c, -1, 0, 0, d, m}, k_, better);
      |                                  ~~~~~~~ ^~~~~~~~~~~~~~~~~~~~~~~~
1 warning generated.
```

(GCC 13.3.0, Ubuntu clang 18.1.3, 둘 다 x86_64.) `b3d8932`의 `optimizer.cpp`와 `c_api.cpp`에 같은 clang 명령을 돌리면 경고가 없다.

정리하면:
- 경고의 정체는 `-Wsign-conversion`이다. **clang은 `-Wconversion`에 `-Wsign-conversion`을 포함**하고, GCC는 C++에서 포함하지 않는다.
  그래서 GCC로 도는 네이티브 CI(VM-16)는 녹색이었고, clang 기반인 Emscripten으로 처음 빌드할 때 이 줄이 걸린다.
  `trip_engine`에는 `-Werror`가 있으므로 경고 하나가 WASM 빌드 실패가 된다.
- "wasm32에서는 `size_t`가 32비트라서"는 원인이 아니다. 위 clang 실행은 `size_t`가 64비트(`unsigned long`)인 x86_64에서도
  같은 경고를 냈다. 문제는 크기가 아니라 부호다.
- 고치는 방법이 "경고 끄기"가 아니라 "명시적 변환"인 이유: `sidx`의 값은 0 이상인 상태 번호이므로 변환은 안전하고,
  캐스트로 "의도한 변환"임을 코드에 적는 것이다. 다른 자리와 표기도 같아진다.

trip::Problem empty_problem(int visits, int days, int modes) {
    trip::Problem p;
    p.visits = visits; p.days = days; p.modes = modes;
    size_t nodes = static_cast<size_t>(visits + 2);
    p.price.assign(nodes * nodes * static_cast<size_t>(days) * static_cast<size_t>(modes), -1);
    p.minutes.assign(p.price.size(), 0);
    p.lodging.assign(nodes * static_cast<size_t>(days), 0);
    p.stay_min.assign(nodes, 0);
    p.stay_max.assign(nodes, 0);
    p.depart_min = 0; p.depart_max = days - 1;
    p.cost_per_minute = 0;
    return p;
}

trip::Problem random_problem(std::mt19937& rng) {
    std::uniform_int_distribution<int> visits(1, 8), days(2, 30), modes(1, 2), price(0, 500), minutes(10, 600),
        lodge(0, 100), stay(0, 2), extra(0, 5), cpm(0, 3), percent(0, 99);
    trip::Problem p = empty_problem(visits(rng), days(rng), modes(rng));
    for (size_t i = 0; i < p.price.size(); i++) {
        p.price[i] = percent(rng) < 25 ? -1 : price(rng);
        p.minutes[i] = minutes(rng);
    }
    for (size_t i = 0; i < p.lodging.size(); i++) p.lodging[i] = lodge(rng);
    for (int c = 1; c <= p.visits; c++) {
        p.stay_min[c] = stay(rng);
        p.stay_max[c] = p.stay_min[c] + extra(rng);
    }
    p.depart_min = std::uniform_int_distribution<int>(0, p.days - 1)(rng);
    p.depart_max = std::uniform_int_distribution<int>(p.depart_min, p.days - 1)(rng);
    p.cost_per_minute = cpm(rng);
    return p;
}

### 2.5 `trip_optimizer/engine/tests/v4_check.mjs` (100줄)

```js
import Module from '../build_wasm/engine.mjs';
import fs from 'fs';
import path from 'path';
import { fileURLToPath } from 'url';

const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);

async function run() {
    const mod = await Module();
    const refPath = path.join(__dirname, 'v4_reference.json');
    if (!fs.existsSync(refPath)) {
        console.error('Reference file missing');
        process.exit(1);
    }
    const content = fs.readFileSync(refPath, 'utf8');
    if (!content.trim()) {
        console.error('Reference file empty');
        process.exit(1);
    }
    const data = JSON.parse(content);
    if (!Array.isArray(data) || data.length === 0) {
        console.error('Reference has zero problems');
        process.exit(1);
    }

    let problems = 0;
    let mismatches = 0;
    const counts = { '-2': 0, '-1': 0, '0': 0, 'plans': 0 };

    for (const p of data) {
        problems++;
        
        const ptrPrice = mod._malloc(p.price.length * 8);
        const ptrMinutes = mod._malloc(p.minutes.length * 8);
        const ptrLodging = mod._malloc(p.lodging.length * 8);
        const ptrStayMin = mod._malloc(p.stay_min.length * 4);
        const ptrStayMax = mod._malloc(p.stay_max.length * 4);
        const ptrOut = mod._malloc(p.out_len * 8);
        
        mod.HEAPF64.set(p.price, ptrPrice / 8);
        mod.HEAPF64.set(p.minutes, ptrMinutes / 8);
        mod.HEAPF64.set(p.lodging, ptrLodging / 8);
        mod.HEAP32.set(p.stay_min, ptrStayMin / 4);
        mod.HEAP32.set(p.stay_max, ptrStayMax / 4);
        
        // Zero-initialize out array
        mod.HEAPF64.fill(0.0, ptrOut / 8, ptrOut / 8 + p.out_len);
        
        const n = mod._trip_optimize(
            p.visits, p.days, p.modes,
            ptrPrice, ptrMinutes, ptrLodging,
            ptrStayMin, ptrStayMax,
            p.depart_min, p.depart_max, p.cost_per_minute,
            p.k, ptrOut, p.out_len
        );
        
        let mismatch = false;
        if (n !== p.expected_n) {
            console.error(`Problem ${problems}: Mismatch in n: got ${n}, expected ${p.expected_n}`);
            if (n === -1) {
                // To get error: we need UTF8 string from C
                // But we don't have to print it to know it's a mismatch.
            }
            mismatch = true;
        } else if (n > 0 || p.out_len > 0) { // check out array even if n <= 0, in case of buffer overwrite? The spec says exactly compare.
            const outActual = mod.HEAPF64.subarray(ptrOut / 8, ptrOut / 8 + p.out_len);
            for (let i = 0; i < p.out_len; i++) {
                if (outActual[i] !== p.expected_out[i]) {
                    console.error(`Problem ${problems}: Mismatch in out[${i}]: got ${outActual[i]}, expected ${p.expected_out[i]}`);
                    mismatch = true;
                    break;
                }
            }
        }
        
        if (mismatch) mismatches++;
        if (n === -2) counts['-2']++;
        else if (n === -1) counts['-1']++;
        else if (n === 0) counts['0']++;
        else if (n > 0) counts['plans']++;
        
        mod._free(ptrPrice);
        mod._free(ptrMinutes);
        mod._free(ptrLodging);
        mod._free(ptrStayMin);
        mod._free(ptrStayMax);
        mod._free(ptrOut);
    }
    
    console.log(`V4 result: ${problems} problems, ${mismatches} mismatches, -2: ${counts['-2']}, -1: ${counts['-1']}, 0: ${counts['0']}, plans: ${counts['plans']}`);
    if (mismatches > 0) {
        process.exit(1);
    }
}

run().catch(err => {
    console.error(err);
    process.exit(1);
});
```

### 3.3 `v4_gen.cpp`

- **C API로 기대값을 만든다(66–68줄).** C++ API(`trip::optimize`)가 아니라 WASM이 부르는 것과 **같은 입구** `trip_optimize`를 부른다.
  그래서 비교 대상은 DP뿐 아니라 경계 검사(`to_int64`, 크기 검사, −1/−2)와 출력 평탄화까지 포함한다.
- **double 사본(57–59줄).** `Problem`의 `price`·`minutes`·`lodging`은 정수 벡터인데 C API는 `double*`를 받으므로 double 벡터로 복사한다.
  JSON에 적는 것도 이 double 벡터이고, JS가 `HEAPF64`에 넣는 것도 이 값이다. 즉 두 쪽이 **바이트 단위로 같은 입력**을 받는다.
- **60줄 `fractional_price`.** 오류 사례에서만 double 사본의 `price[0]`을 10.5로 바꾼다. 이 값은 정수가 아니므로 `c_api.cpp`의
  `to_int64`가 거부해 −1이 나온다(4장 (a)에서 rev 1과 비교). 직접 확인: 같은 입력을 네이티브에서 부르면
  `n=-1`, `trip_last_error()` = `price and minutes must be whole numbers`.
- **61–64줄 출력 버퍼.** 길이는 `trip_output_size(visits, k)`, 단 `out_len_override >= 0`이면 그 값(버퍼 부족 사례용).
  `std::vector<double> out(n)`은 0으로 초기화된다. 계획이 k개보다 적으면 나머지 칸은 0으로 남는다.
- **70–95줄 JSON 출력.** 문제 하나가 객체 하나. `expected_out`은 **버퍼 전체**(0으로 남은 꼬리까지)다. `stay_min`/`stay_max`는 `int`라서
  따로 `print_json_int_array`로 쓴다(JS에서 `HEAP32`로 들어간다).
- **85–93줄의 빈 `if`.** 안에 주석만 있고 아무 일도 하지 않는다(작성 중 고민이 남은 것). 결론은 92줄 주석대로 "버퍼 전체 출력"이고
  실제 동작은 94줄이 한다. 손으로 칠 때는 빼도 된다.
- **109줄 주석 `(negative price)`는 틀렸다.** 실제로는 소수 가격(10.5) 사례다. rev 1에서 남은 주석이다.
- **`main`(98–119줄).** 시드 99로 고정한 `std::mt19937` → 매번 같은 파일. 무작위 1010개(k = 4) + 입력 오류 1개 + 버퍼 부족(`out_len = 1`) 1개
  = 1012개. 마지막 원소 뒤에는 쉼표를 붙이지 않는다(`is_last`). `uniform_int_distribution`의 결과는 표준 라이브러리 구현마다 다를 수
  있지만, 문제를 만드는 쪽은 네이티브 하나뿐이고 WASM은 JSON에 적힌 숫자를 읽으므로 V4에는 영향이 없다.
- **왜 `setprecision(17)`이면 double이 왕복하나(99줄).** `std::cout`의 기본 정밀도는 유효숫자 6자리다. IEEE 754 double(53비트 가수)은
  유효숫자 **17자리**(`std::numeric_limits<double>::max_digits10`)로 쓰면 그 문자열을 다시 읽었을 때 언제나 원래와 같은 double로
  돌아온다. 기본 형식(`%g` 계열)에서는 지수가 정밀도보다 작으면 일반 표기를 쓰므로, 1e17 미만 정수는 지수 표기 없이 정수 그대로 나온다.
  JS의 `JSON.parse`는 문자열을 가장 가까운 double로 읽으므로 C++이 계산한 것과 같은 비트가 된다. 이 문서를 쓰며 돌려 본 값:

```text
기본 정밀도   : 1234567 → 1.23457e+06   10.5 → 10.5   0.1 → 0.1                   9007199254740991 → 9.0072e+15
setprecision(17): 1234567 → 1234567      10.5 → 10.5   0.1 → 0.10000000000000001   9007199254740991 → 9007199254740991
node: JSON.parse("[1.23457e+06, 0.10000000000000001]") → [ 1234570, 0.1 ]
```

  6자리로는 1234567이 1234570으로 바뀌어 돌아온다. 17자리의 `0.10000000000000001`은 보기에는 길지만 읽으면 정확히 원래의 0.1(가장 가까운 double)이다.
  `setprecision`은 스트림에 남는 설정이므로 `main` 첫 줄에서 한 번만 걸면 이후 모든 출력에 적용된다.

### 3.4 `v4_check.mjs`

- **1줄 정적 `import`.** `../build_wasm/engine.mjs`(= `engine/build_wasm/`)가 없으면 코드가 한 줄도 돌기 전에 모듈 로딩 오류로 Node가
  0이 아닌 코드로 끝난다. WASM 빌드가 빠지면 V4 단계가 실패한다.
- **6–7줄.** ES 모듈에는 `__dirname`이 없어서 `import.meta.url`로 만든다. 기준 파일은 이 스크립트 옆(`tests/`)에서 찾는다.
- **11–25줄 기준 파일 방어.** 파일 없음 → `Reference file missing`, 빈 파일 → `Reference file empty`, 배열이 아니거나 길이 0 →
  `Reference has zero problems`, 셋 다 `process.exit(1)`. 핵심은 **"0문제, 0불일치"가 통과로 끝나지 않게** 하는 것이다.
  rev 1(`JSON.parse(fs.readFileSync(...))` 한 줄)에서도 파일이 없거나 비면 예외가 나서 97–100줄 `catch`가 exit 1로 끝냈다. rev 1에서 실제로
  통과해 버리는 구멍은 내용이 `[]`인 경우였고, rev 2의 22줄 검사가 그것을 막는다.
- **34–39줄 `_malloc`.** 바이트 단위다. double은 8바이트, `int`는 4바이트라서 `length * 8`, `length * 4`.
- **41–45줄 포인터 산술 `ptr / 8`, `ptr / 4`.** `mod.HEAPF64`는 WASM 메모리 **전체**를 덮는 `Float64Array`, `mod.HEAP32`는 같은 메모리를
  덮는 `Int32Array`다. 타입 배열의 첨자는 바이트가 아니라 **원소 번호**이므로 바이트 주소 `ptr`을 원소 크기로 나눈다.
  `malloc`은 double을 담을 수 있게 정렬된(8의 배수) 주소를 주므로 나눗셈이 정수로 떨어진다. `set(배열, 시작 첨자)`가 JS 배열을 그 자리에 복사한다.
- **48줄 `fill(0.0, ...)`.** 출력 버퍼를 0으로 채운다. 네이티브 쪽 `std::vector<double> out`도 0으로 시작하므로, 계획이 k개보다 적어
  남은 꼬리까지 두 쪽이 같아야 한다. `malloc`은 메모리를 비워 주지 않으므로(앞 문제가 쓴 값이 남을 수 있음) 이 줄이 없으면 꼬리가 달라질 수 있다.
- **50–56줄 호출.** WASM32에서 포인터는 그냥 숫자(바이트 주소)라서 JS 숫자로 넘긴다. 인자 순서는 `c_api.h`의 선언 그대로다.
- **58–75줄 비교.** 먼저 반환값 `n`, 같으면 출력 버퍼 **전체**를 `!==`(정확한 double 같음)로 비교하고 첫 불일치에서 멈춘다.
  허용 오차는 없다. 엔진은 정수 계산이고 출력은 2^53 미만 정수라서 "정확히 같음"이 올바른 기준이다.
  66줄 조건 `n > 0 || p.out_len > 0`은 이 데이터에서 언제나 참이다(`out_len`이 최소 1). 즉 0, −1, −2 사례에서도 버퍼가 건드려지지
  않았는지(전부 0인지)까지 비교한다. 61–64줄의 `if (n === -1)` 블록은 주석뿐이다(연습 문제 1).
- **67줄 호출 뒤에 `mod.HEAPF64`를 다시 읽는다.** `ALLOW_MEMORY_GROWTH`에서 메모리가 늘면 WASM 메모리의 `ArrayBuffer`가 새것으로
  바뀌고, 옛 버퍼를 덮던 타입 배열은 분리(detached)되어 길이가 0이 된다. Emscripten은 늘린 뒤 `HEAPF64` 등을 새 버퍼로 다시 만든다.
  `trip_optimize` 안에서 DP가 `vector`를 잡으며 메모리를 늘릴 수 있으므로, 호출 **전에** `const heap = mod.HEAPF64`처럼 붙잡아 둔 뷰로
  결과를 읽으면 안 된다. 이 코드는 뷰를 변수에 붙잡지 않고 쓸 때마다 `mod.HEAPF64`를 새로 읽는다(41–48줄도 모든 `_malloc` 뒤에 읽는다).
  SPEC 4.1의 "메모리가 늘면 HEAP 뷰가 바뀌므로 호출 후에 매번 다시 읽는다"가 이 줄이다. (이 시험에서 메모리가 실제로 늘어나는지는 확인하지 않았다.)
- **77–81줄 종류별 개수.** −2, −1, 0, 계획 있음. rev 2에서 추가. 이 줄 덕에 로그만 보고 "−1 사례가 실제로 −1로 시험되었는지"를 알 수 있다(4장).
- **83–88줄 `_free`.** 문제마다 빌린 6개를 돌려준다. 안 하면 1012문제 동안 힙이 계속 커진다.
- **91–94줄.** 요약 한 줄을 찍고 불일치가 하나라도 있으면 exit 1.

## 6. 연습 문제

1. **−1일 때 오류 문자열 찍기.** `v4_check.mjs` 61–64줄에서 `mod._trip_last_error()`가 돌려주는 포인터를 `mod.UTF8ToString(ptr)`로
   문자열로 바꿔 출력한다. `UTF8ToString`이 `mod`에 없다고 나오면 CMakeLists.txt 18줄 링크 옵션에 `"-sEXPORTED_RUNTIME_METHODS=UTF8ToString"`을
   추가한다. 일부러 −1 사례의 `expected_n`을 바꿔 불일치를 만든 뒤, 로그에 `price and minutes must be whole numbers`가 나오는지 CI에서 본다
   (이 문자열은 같은 입력을 네이티브에서 부를 때 `trip_last_error()`가 돌려준 값이다).
2. **정확성을 일부러 깨기.** `v4_gen.cpp` 99줄을 지우고 `random_problem`의 `price(0, 500)`을 `price(0, 5000000)`으로 바꾼다.
   먼저 로컬에서 기준 파일에 `e+06`이 섞여 나오는지 `grep -c 'e+06' build/v4_reference.json`으로 보고, push해서 V4가 실패하는지,
   첫 불일치가 `n`인지 `out[i]`인지 확인한다. 그다음 99줄만 되살려 다시 녹색이 되는지 본다.
3. **HEAP 뷰를 붙잡아 두는 버그.** `v4_check.mjs`의 `run()` 맨 앞에서 `const F64 = mod.HEAPF64;`로 한 번만 잡고 모든 `mod.HEAPF64`를
   `F64`로 바꾼다. 무엇이 일어날지 먼저 예측한다(메모리가 늘지 않으면 아무 일도 없을 수 있다). 그다음 큰 문제(visits 8, days 30)를 앞에
   두고 다시 돌려 본다. 결과가 어떻든 "왜 그 결과인지"를 3.4절의 detached 설명으로 적어 본다.
4. **경고 집합 비교.** `e081fb3`의 `optimizer.cpp`에 대해 `g++ -Wconversion`, `g++ -Wconversion -Wsign-conversion`, `clang++ -Wconversion`을 각각
   돌려 경고 개수를 센다. 네이티브 CI에서도 clang과 같은 경고를 잡으려면 CMakeLists.txt 12줄에 무엇을 더하면 되는지, 그때 엔진 다른 곳에서
   새 경고가 나오는지 본다.
5. **입력 오류 사례 하나 더.** `main`에 `visits = 11`인 사례를 추가한다(`empty_problem(11, 2, 1)`). C API 첫 검사(`visits must be 1..10`)로 −1이
   나와야 한다. 마지막 원소의 `is_last` 처리를 바꾸는 것을 잊지 말 것. 로컬 python 한 줄의 개수가 `-1: 2`, 합계 1013이 되는지 확인한다.
6. **방어 코드 읽기.** 기준 파일 내용이 (가) 없음, (나) 빈 문자열, (다) `[]`, (라) `[{}]`일 때 rev 1과 rev 2의 `v4_check.mjs`가 각각 어디서
   어떤 메시지·종료 코드로 끝나는지 표로 적는다. (라)는 두 판 모두 전용 검사가 없다. 그래도 단계가 실패하는지, 실패한다면 몇 번째 줄에서 어떤
   예외가 나서 어느 `catch`가 받는지 적고, "문제 객체에 필요한 필드가 다 있는지"를 미리 검사하는 코드를 써 본다.
