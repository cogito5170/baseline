# 01 · VM-16 엔진 CI 작업 (analy_agent `e081fb3`, baseline issue #40)

바뀐 파일: `.github/workflows/engine.yml` (새 파일, 33줄). 엔진 소스는 그대로.

## 원문

```yaml
name: trip_optimizer engine CI

on:
  push:
    paths:
      - 'trip_optimizer/**'
      - '.github/workflows/engine.yml'
  pull_request:
    paths:
      - 'trip_optimizer/**'
      - '.github/workflows/engine.yml'

jobs:
  engine:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Configure CMake
        run: |
          cd trip_optimizer/engine
          mkdir build && cd build
          cmake -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_FLAGS="-Werror" ..
      
      - name: Build
        run: |
          cd trip_optimizer/engine/build
          make
          
      - name: Test
        run: |
          cd trip_optimizer/engine/build
          ctest --output-on-failure
```

## 해설

| 줄 | 무엇 | 왜 |
|---|---|---|
| `name:` | 워크플로 이름. Actions 화면에 이 이름으로 보인다 | 저장소에 워크플로가 여러 개(qa-pipeline, embedded-qa)라 구분용 |
| `on: push / pull_request` + `paths:` | `trip_optimizer/` 아래나 이 파일이 바뀔 때만 실행 | BMS 문서만 바꾼 커밋에서 엔진 CI를 돌리지 않아 시간 절약. 워크플로 파일 자신을 넣는 이유: CI를 고친 커밋은 CI로 확인돼야 한다 |
| `jobs: engine:` | 작업 하나. 이름 `engine`은 SPEC 6.2 표의 작업 이름과 같다 | 다음 단계에서 `web`, `deploy` 작업이 이 옆에 붙는다 |
| `runs-on: ubuntu-latest` | GitHub가 주는 깨끗한 리눅스 VM | 매번 새 환경이라 '내 컴퓨터에서만 되는' 문제를 잡는다 |
| `actions/checkout@v4` | 저장소 코드를 내려받음 | (참고) 로그에 Node 20 지원 종료 경고 → VM-17에서 새 버전으로 올리게 했다 |
| `Configure CMake` | `build/` 폴더에서 `cmake -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_FLAGS="-Werror" ..` | Release = 최적화 빌드(성능 시험이 의미 있게). `-Werror`는 경고를 오류로. 엔진 라이브러리는 CMakeLists.txt에 이미 `-Wall -Wextra -Werror -Wconversion -Wshadow`가 있어서, 여기 플래그는 시험 코드까지 넓히는 효과 |
| `Build` | `make` | CMake가 만든 Makefile로 컴파일. 첫 빌드에서 GoogleTest v1.15.2를 FetchContent로 받아온다 |
| `Test` | `ctest --output-on-failure` | 10개 시험 실행. 실패할 때만 시험 출력 전체를 보여 줘서 로그가 짧다 |

## 손 코딩 순서
1. 빈 저장소에 `.github/workflows/` 폴더를 만들고 `name`과 `on: push`만 있는 워크플로에 `echo hello` 단계 하나로 시작 → push → Actions 탭에서 실행 확인.
2. checkout 단계 추가 → `ls` 단계로 파일이 보이는지 확인.
3. Configure / Build / Test 단계를 하나씩 추가하고 매번 push해서 어느 단계에서 깨지는지 본다.
4. `paths:` 필터를 넣고, trip_optimizer 밖 파일만 바꾼 커밋에서는 실행되지 않는 것을 확인.

## 연습 문제
1. 엔진 소스에 일부러 쓰지 않는 변수를 하나 넣고 push → 어느 단계가 어떤 메시지로 실패하는지 확인 (`-Werror`의 효과).
2. `make` 대신 `cmake --build . -j` 로 바꿔 보기. 무엇이 같고 무엇이 다른가 (생성기 독립성, 병렬 빌드).
3. `ctest`에 `-R CApi` 를 붙이면 무엇이 실행되나.
4. 같은 파일을 `pull_request`만 남기면 작업 브랜치 push에서 CI가 도는가?
